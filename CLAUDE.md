# Guf App — Contexto do projeto

App PWA de evolução fitness (musculação). Interface em **português do Brasil**. Mobile first.
Usuário registra treinos NA ACADEMIA, com uma mão, entre séries: registrar uma série deve levar menos de 3 segundos.
Nome da marca: **guf** (Guf App) — nunca "guff" (o design system do Claude Design ainda usa "guff" em alguns nomes; corrigir ao implementar).

## Funcionalidades do MVP
- Autenticação: e-mail/senha e Google, com vinculação do Google a conta existente (feita pelo Supabase quando o e-mail confirmado é o mesmo). Login com Apple fica para a fase do app iOS.
- Projetos (grupos de rotinas) → Rotinas (exercícios planejados com séries/reps/descanso)
- Treino por rotina OU treino livre (sem rotina); registro de carga, repetições e tipo de série
- Histórico por exercício (carga máxima, volume, 1RM estimado, recordes pessoais)
- Calendário de dias treinados; streak de semanas
- Medidas corporais (módulo opcional com consentimento LGPD específico)
- Privacidade: exportar dados, revogar consentimento, excluir conta

## Stack
- Monorepo: Turborepo + pnpm
- Web: Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui
- Dados: @supabase/supabase-js + TanStack Query (+ `@tanstack/react-query-devtools` como devDependency, aberto só no `next dev` pelo botão no canto superior direito; montado no `QueryProvider` em `shared/libs/query-provider.tsx`)
- Formulários: React Hook Form + Zod (integração via @hookform/resolvers)
- Gráficos: Recharts (instalado no apps/web; cores via `var(--color-…)` dos tokens; o `<figure>` de cada gráfico leva `CHART_WITHOUT_FOCUS_RING` de `shared/helpers/chart.ts`: o Recharts 3 deixa a área focável e o toque mostrava o contorno de foco em volta do gráfico; o balão do ponto tocado e as setas do teclado continuam; o `ProgressChart` do design system, SVG próprio usado na Evolução do perfil e nas medidas, tem a mesma agulha com balão: tocar/arrastar na horizontal, setas, Home/End e Esc no teclado; textos por `pointLabels`, `pointDetails` e `formatValue`) · Datas: date-fns (só em packages/core; o app usa as funções de `dates.ts`) · Ícones: lucide-react
- Animações: Anime.js (v4), React Bits, Motion — sempre respeitando prefers-reduced-motion. **Motion instalado** (`motion@13.4.6`, `motion/react`): `MotionProvider` nos Providers (`LazyMotion` domMax `strict` → usar `m.*`, nunca `motion.*`; `MotionConfig reducedMotion="user"`). Primitivas em `shared/components/ds/motion.tsx`: `Collapse` (abrir/fechar com altura), `PresenceRow` (linha que entra/sai), `LayoutItem` + `LAYOUT_ITEM_PROPS` (desliza ao reordenar/remover; dentro de `AnimatePresence initial={false} mode="popLayout"`, contêiner `relative`). Entradas simples continuam nos keyframes CSS (`animate-guf-*`). Motion vai num invólucro, nunca no mesmo elemento de um keyframe com `transform` (a animação CSS sobrescreve o transform do Motion). **Anime.js instalado** (`animejs@4.5.0`; por enquanto só no boneco 3D das medidas, animando números que o shader lê). Na v4 uma lista vira VÁRIOS alvos: animar objetos (`{ value }`), nunca números de um array (quebrava o toque no músculo). React Bits ainda não instalado.
- Sons: registry **soundcn** pela CLI do shadcn (`pnpm dlx shadcn add @soundcn/<som>`; som em base64 no próprio arquivo, funciona offline; motor em `src/shared/sound/sound-engine.ts`). Usar só sons CC0 de origem conhecida (ex.: Kenney).
- PWA: Serwist (`@serwist/cli` + `serwist`; o `esbuild` é dependência obrigatória do CLI, só no build) · Offline do treino em andamento: Dexie (IndexedDB)
- IA (GUF AI): **AI SDK da Vercel** — `ai@7.0.131` + `@ai-sdk/react@4.0.134` no app (useChat) e `npm:ai@7.0.131` + `npm:@ai-sdk/google@4.0.90` na Edge Function `guf-ai` (aprovados em 2026-10-21). Provedor atual: Google Gemini (API gratuita, só beta); trocar = `supabase/functions/guf-ai/model.ts`. Na v7: `instructions` (não `system`), `isStepCount`, `onEnd`, `result.stream`.
- Imagens dos stories: `modern-screenshot` (4.7.0; elemento → PNG no aparelho, embute fontes; aprovada em 2026-10-16)
- 3D: **three.js** (`three@0.186.1` + `@types/three` em dev; aprovado em 2026-10-23), só no boneco anatômico das medidas (`features/body-measurements/helpers/body-scene.ts`, carregado por import dinâmico ao abrir `/medidas`). Modelo `public/models/boneco.glb` = X Bot do Mixamo (Adobe), o mesmo `Xbot.glb` dos exemplos do three.js r160 (conferido byte a byte com o do protótipo): uso livre, inclusive comercial, sem crédito obrigatório; não distribuir o arquivo solto fora do app. Fica fora do pré-cache do service worker (2,9 MB).
- Hospedagem: produção na **Cloudflare** (Workers com assets estáticos, projeto `guf-pwa`; `wrangler.jsonc` na raiz publica `apps/web/out`; build `pnpm --filter @guf/web... build`, deploy `npx wrangler deploy`); painel em outro Worker, `guf-admin` (`apps/admin/wrangler.jsonc`, deploy `npx wrangler deploy -c apps/admin/wrangler.jsonc`, Root directory também na raiz; `docs/admin-panel.md` § 5.5), domínio oficial **https://treino.gufapp.com.br** (definido em 2026-11-06). A Vercel (`gufapp.vercel.app`) segue no ar até a migração. Domínio novo = outro site para o navegador (app instalado, fila offline, notificações e preferências do aparelho não migram). Ao trocar o endereço: Redirect URLs e Site URL do Supabase Auth, secrets `ALLOWED_ORIGINS` (acrescentar; um só para todas as Edge Functions) e `APP_URL`. Em todos os casos, site estático.
- Futuro: app React Native (Expo) reaproveitando os pacotes compartilhados
- **Google Play (decisão de 2026-11-06):** o PWA vai para a Play Store empacotado como **TWA** (Bubblewrap/PWABuilder, fora do monorepo) e, quando o app React Native ficar pronto, ele **substitui o TWA no mesmo anúncio** (mesmo nome de pacote, mesma chave de envio com Play App Signing, `versionCode` maior). Passo a passo, `assetlinks.json` e exigências da Play em `docs/play-store-twa.md`. **Pagamento (decisão de 2026-11-07): dentro do TWA o Pro é comprado pelo Google Play Billing; no navegador, pelo Stripe** (ver "Google Play Billing" em Planos). Nome do pacote e chaves nunca mudam depois do 1º envio.
- Não adicionar bibliotecas fora desta lista sem perguntar.

## Padrões de engenharia
- As skills ficam em `.claude/skills/`; **`code-standards` é a porta de entrada** (roteia para as demais). Conceitos em `.claude/patterns/`.
- Antes de criar componente, hook, serviço ou instalar lib → `/code-attention` (varredura de duplicatas e do que já existe).
- Ao escrever ou refatorar → `/code-patterns` e `/code-structure` (prioridade: princípios SOLID e arquitetura de pastas).
- Ao documentar → `/code-docs`; para revisar → `/code-review-guf` (o `/code-review` é o comando embutido do Claude Code).
- **Regras absolutas:** sem IIFE em JSX/TSX · sem função multi-propósito · sem comentário inline explicando "o que fez" (comentário de *porquê* é permitido) · sem `any` sem justificativa.
- Toda tarefa termina com a revisão de encerramento da `code-standards`.
- Em conflito, este `CLAUDE.md` vence as skills. As bases não mudam: site estático, backend e banco só no Supabase, PWA e treino offline-first.

## Regras de arquitetura (OBRIGATÓRIAS)
1. **Site estático:** `output: "export"` no Next.js. NÃO usar Server Actions, Route Handlers, middleware de servidor ou SSR com dados. Tudo roda no cliente.
2. **Rotas dinâmicas:** evitar `/treino/[id]`. Usar rotas fixas com query string (`/treino?id=...`) lidas com `useSearchParams` (envolver em `<Suspense>`).
3. **Segurança no banco:** o RLS do Supabase protege os dados. No front, usar APENAS a chave pública `publishable` (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`). NUNCA usar `service_role`/`secret` no front. Cliente: `createGufClient` (packages/api, PKCE + sessão persistente) via `getSupabaseClient()` em apps/web/src/shared/libs/supabase.ts. `NEXT_PUBLIC_SUPABASE_URL` é só a URL base do projeto (`https://<ref>.supabase.co`, sem `/rest/v1`).
4. **Lógica reutilizável fora do app web:** cálculos em `packages/core`, validações em `packages/schemas`, consultas em `packages/api`. Componentes React ficam em `apps/web`.
5. **Não alterar o banco pelo front nem pelo painel.** Mudanças de schema só via nova migration em `supabase/migrations/` (`npx supabase migration new nome`). Não editar migrations já existentes.
6. **Tipos do banco:** importar de `packages/types/src/database.ts`. Regenerar com `npx supabase gen types typescript --linked > packages/types/src/database.ts` após qualquer migration (gerar antes num arquivo temporário para não truncar o atual se o comando falhar). No Windows PowerShell 5.1, o `>` grava em UTF-16: converter para UTF-8 antes de substituir o `database.ts` (ou gerar pelo Git Bash). Nesta versão da CLI o `gen types` pode não achar o login que os outros comandos acham; nesse caso, rodar no terminal do usuário.
7. **Pastas por feature (apps/web):** código de uma funcionalidade fica em `src/features/<feature>/` (subpastas `api/`, `hooks/`, `helpers/`, `constants/`, `components/`, `providers/`, `ui/`, só as que forem usadas). Código usado por 2+ features ou sem domínio vai para `src/shared/`; store externo, para `src/store/global/*.store.ts`. Nunca recriar `components/`, `hooks/`, `lib/` ou `providers/` na raiz de `src/`.
8. **Barrel e dependências:** cada feature expõe o que outras partes usam em `index.ts`; `app/` e outras features importam só `@/features/<f>` (nunca o interior). Dentro da feature, importar pelo caminho. `shared/` e `store/` NUNCA importam `features/`; a composição entre features fica em `app/` (ex.: `app/providers.tsx`). `shared/` não tem barrel geral (importar pelo caminho; o design system tem o seu em `shared/components/ds`).
9. **Camadas (SOLID):** `app/` (rota) → `features/<f>/ui` (tela, sem regra de negócio) → `features/<f>/hooks` e `api/` (orquestração e TanStack Query) → `packages/api` (único acesso ao Supabase) / `shared/offline` (fila) → Supabase. Regra de negócio em `packages/core`, validação em `packages/schemas`. A tela depende do contrato pela fonte `useXxxSource()` (API real ou mock), nunca do cliente direto. Sem `fetch` nem `supabase.from()` no app.
10. **Onde colocar o novo:** usado por uma feature → nela; segundo uso em outra feature → `shared/`; regra ou consulta que o app mobile também vai usar → `packages/`. Ordem para uma funcionalidade nova: função em `packages/api` (+ regra em `core`, schema em `schemas`) → mock em `src/mocks/` → hook em `api/` → tela em `ui/` → exportar no `index.ts` → `page.tsx`. Detalhes e justificativa em `docs/architecture.md`.

## Padrões do front (apps/web)
- **Estilo:** classes utilitárias do Tailwind usando os tokens do `@theme` (ex.: `bg-surface`, `text-fg`, `rounded-lg`). Sem estilos inline (`style={{…}}`), exceto valores realmente dinâmicos (ex.: % de uma barra de progresso, atraso escalonado de animação). Sem CSS por componente. O CSS global fica só para tokens, reset, fontes e keyframes (`packages/ui/styles/` + `src/app/globals.css`).
- **Cores de texto:** `text-fg`, `text-fg-secondary`, `text-fg-muted`. Atenção: `text-primary` é o volt (alias do shadcn), não a cor do texto. Misturas de cor (`color-mix`) viram tokens nomeados no `@theme`, nunca classes arbitrárias com `var()`.
- **Componentes:** reutilizar os do design system (`packages/ui`, importado no app por `@/shared/components/ds` e no painel por `@guf/ui`) antes de criar novos (varredura da `/code-attention`); componente novo só se não existir. Partes de uma tela ficam em `features/<feature>/components/`, a tela em `features/<feature>/ui/` (`XScreen`). Lista ou tabela grande vira componente próprio; nada de lógica de negócio no JSX.
- **Reordenar listas:** sempre `useHoldReorder` (`apps/web/src/shared/hooks/`), o mesmo do treino em andamento, + positions sequenciais (`changedPositions` em packages/core). Usado no treino, na lista de rotinas do projeto (`features/projects/components/routine-list.tsx`) e nos exercícios do editor de rotina (`RoutineExerciseCard`). Segurar o cabeçalho do card liga o modo; o card fica com altura fixa (`itemPx`, ex.: 72 px na rotina; o destino é calculado por slot fixo), balança, o menu do card vira a alça e o cabeçalho tem `select-none`, sem menu de contexto nem arraste nativo de texto. Sem reordenar pelo teclado (pendência de acessibilidade; o antigo `usePointerReorder`, com setas, foi removido porque copiava texto no toque). O `ReorderList` do design system usa o arrastar nativo do HTML5, que não funciona no toque do celular — não usar em telas do app.
- **Camadas fixas na tela** (folhas `BottomSheet`/`ConfirmDialog` com `placement="screen"`, seletor de exercícios e qualquer tela cheia nova): renderizar por portal no `<body>` (`ScreenPortal` do design system). Um ancestral com `transform` (ex.: a animação de entrada `animate-guf-rise`) vira a referência do `position: fixed` e a camada "escondida" aparece no meio da página. Camadas: folhas `z-[60]`, diálogos `z-[70]` (acima de telas cheias `z-50`).
- **Fechar o `BottomSheet`:** toque fora, Esc ou arrastar para baixo pela alça/título (`useSheetDrag` em apps/web/src/shared/hooks; fecha ao soltar com > 30% da altura ou gesto rápido, senão volta). Só a área do topo arrasta, para não brigar com campos e rolagem do conteúdo. Sem `onClose`, a folha não fecha por nenhum desses meios. O `ConfirmDialog` ainda NÃO fecha com Esc nem prende o foco (pendência de acessibilidade).
- **Toques repetidos que gravam** (ex.: + / − da meta semanal): `useCoalescedSave` (apps/web/src/shared/hooks; lógica pura `createCoalescedSaver` em packages/core/src/coalesce.ts). A tela muda na hora e só o último valor é enviado 600 ms depois do último toque; nunca duas gravações ao mesmo tempo; voltar ao valor salvo não envia; ao sair da tela, envia o que estiver esperando.
- **Toast** (protótipo `Toast.dc.html` do Claude Design): `const id = useAppShell().showToast(título, { tone, message, icon, actionLabel, onAction, onClose, haptic })`. Tipos (`tone`, sempre informar): `success` · `error` (role alert) · `warning` · `info` · `pr` (troféu, brilho dourado) · `undo` ("Desfazer"; ação em volt) · `loading` (GufLoader 04, não expira; trocar com `updateToast(id, título, opções)`); `dismissToast(id)`. O tipo é lido pelo ícone, cor e título, nunca só pela cor; mensagem longa vai em `message`. Pilha (`ToastStack` + `createToastStore` em `packages/ui/src/toast-store.ts`, reexportado por `src/store/global/toast.store.ts`): 5 s com barra de tempo, até 3 visíveis, mouse/foco/toque expande e pausa, arrastar para o lado (> 90 px) dispensa; portal no `<body>` em `z-[65]`. `onClose` = sumiu SEM a ação (use para confirmar remoções adiadas). Vibra em sucesso/recorde (`haptic: false` quando a tela já vibrou). Posição medida, sem regra por tela: toda barra fixa no rodapé (menu inferior, mini card, barra do `EditorFrame`, "Salvar", descanso do treino, seletor e o `BottomSheet` aberto) espalha `BOTTOM_BAR_PROPS` (`data-bottom-bar`; contrato em `packages/ui/src/ds/bottom-bar.ts`, reexportado pelo hook) e o AppShell (`useBottomClearance`, apps/web/src/shared/hooks/use-bottom-clearance.ts) põe a pilha 16 px acima da barra visível mais alta, acompanhando quadro a quadro enquanto a barra desliza (classe/estilo trocados, transição ou animação; teto de 1 s): com a folha aberta o aviso sobe junto e fica acima dela, e desce quando ela fecha; sem barra, 16 px + área segura do fundo. Barra nova = só a marca (o antigo `useRaisedToast` saiu). Toast fixo fora da pilha (ex.: nova versão do PWA): componente `Toast` direto.
- **Fontes:** Inter (interface) e Barlow Condensed (números, sempre `tabular-nums`), locais via `next/font/local` em `src/app/fonts/`.
- **Dados fictícios:** sempre em `apps/web/src/mocks/`, com a **mesma assinatura** das funções reais de `packages/api` (mesmos nomes, parâmetros e retorno, inclusive erros), validada com `satisfies <Contrato>Api`. Integrar = trocar a importação.
- **Contrato das funções de `packages/api`:** `(client, input) => Promise<{ data, error }>` (nunca os dois); `error` = `{ code, message }` com mensagem pronta em português (o que aconteceu e como resolver).
- **Só em desenvolvimento:** páginas com extensão `.dev.tsx` (ex.: `/design-system`, `/pngs` — galeria de todos os PNGs exportáveis por estilo, com dados de exemplo Força · Cardio · Força + cardio, tema, opacidade e "Baixar PNG", `StoryGalleryScreen` em features/share/ui, reconhecidas só no `next dev` via `pageExtensions`) e parâmetros de teste como `?estado=` (protegidos por `process.env.NODE_ENV === "development"`, eliminados do build de produção).
- **Rotas e proteção (no cliente; quem protege os dados é o RLS):** grupo `(app)` exige sessão e aceite (`RequireAuth` + `AppShell` com menu inferior); `(auth)` = /login e /cadastro (logado segue para o app); `(consent)` = /aceite. `?next=` só aceita caminhos internos (`safeNextPath`). Sem internet o portão não bloqueia: a consulta de documentos pendentes pausada ou com erro de rede deixa o app abrir (treino offline) e roda de novo ao reconectar, levando ao `/aceite` se houver pendência (`RequireAuth` em features/auth/components/guards.tsx); só outros erros mostram "Não foi possível verificar sua conta".
- **Datas:** sempre no fuso local do aparelho (`packages/core/src/dates.ts`); semana de **domingo a sábado** (`WEEK_STARTS_ON = 0`, `startOfLocalWeek`, `WEEKDAY_INITIALS` em dates.ts; no banco, `get_streak` agrupa pelo domingo — migration `20261017184353_week_starts_sunday`). Nunca escrever listas de dias começando na segunda.
- **Erros da API:** códigos e mensagens em `packages/api/src/result.ts` (`toApiError`); a lista completa (código do banco → código do app, por módulo) fica em [docs/reference/api-errors.md](docs/reference/api-errors.md). Código novo → `result.ts` + essa lista.

## Regras de negócio
- **Repetições da rotina:** fixas ou faixa, escolhidas por exercício. No banco, `routine_exercises.target_reps_min`/`target_reps_max` (smallint, 1–100): máximo nulo = fixas, máximo maior que o mínimo = faixa, os dois nulos = não definidas. O modo não é gravado (vem do máximo). No app, `RepTarget` (packages/core/src/rep-range.ts). A coluna de texto `target_reps` está descontinuada (sempre nula, check) e sai numa migration futura.
- **Peso sempre em kg no banco**; conversão para lb só na exibição (`profiles.weight_unit`).
- **performed_on** = data LOCAL do usuário (`format(new Date(), 'yyyy-MM-dd')`), nunca deixar o padrão do banco (UTC).
- **Um treino em andamento por vez** (o banco recusa outro): ao abrir o app, retomar o treino aberto. Com treino aberto, a aba "Treinar" e a folha "Iniciar treino" oferecem só retomar.
- **Iniciar treino:** cria a sessão (nome da rotina como snapshot ou "Treino livre") e copia os exercícios planejados para session_exercises; se a cópia falhar, apaga a sessão recém-criada.
- **Excluir projeto:** qualquer projeto exceto o Favoritos. Exclui junto as rotinas e os exercícios planejados (`routines.project_id` com `on delete cascade`); os treinos feitos continuam no histórico (`workout_sessions.routine_id` vira nulo, o nome fica). Excluir o ativo deixa o usuário sem projeto ativo.
- **Um projeto ativo por usuário:** trocar o ativo SEMPRE pela RPC `activate_project` (atômica); nunca em duas gravações pelo app. Desativar (ficar sem projeto ativo) ou arquivar o ativo é uma gravação simples (`is_active = false`; ao arquivar, também desativar).
- **Projetos e rotinas só com internet:** criar, editar, reordenar e arquivar projetos, rotinas e exercícios planejados exige conexão (sem fila offline). Sem internet, as ações de edição ficam bloqueadas com o aviso "Sem conexão – para criar ou editar rotinas, conecte-se à internet." e o conteúdo já carregado continua visível.
- **Trocar exercício de um treino:** apagar o session_exercise e criar outro (mantém número e tipo das séries).
- **Tempo de treino:** `started_at`/`finished_at` = início e fim; tempo efetivo = soma dos períodos de `workout_active_periods` (várias pausas; no máximo um período aberto por treino) e fica em `workout_sessions.active_seconds` ao finalizar. A duração exibida é sempre a efetiva (`active_seconds` ?? fim − início para treinos antigos). Relógio no front: `WorkoutClock` em `packages/core/src/session.ts`.
- **Séries planejadas ao iniciar:** `target_sets` da rotina (sem meta: nº de séries do último desempenho, mínimo 3). Carga e repetições pela opção da rotina `routines.auto_progress` ("Atualizar carga e repetições automaticamente", padrão ligada): ligada = último desempenho ou, sem histórico, `target_reps_min`; desligada = carga planejada `routine_exercises.target_weight_kg` e `target_reps_min` (vazio se não houver). Regra em `plannedSetValues` (packages/core/src/workout.ts), usada por `startWorkout`.
- **Atualizar a rotina ao finalizar:** treino iniciado por rotina pergunta, depois de confirmar "Finalizar", "Atualizar a rotina?" (`ConfirmDialog` `balanced`: Manter rotina · Atualizar rotina); "Atualizar rotina" pede uma segunda confirmação ("Substituir a rotina?", Voltar · Sim, atualizar), porque troca o que estava planejado e não dá para desfazer. Atualizar = RPC `update_routine_from_workout(p_session_id)` depois do `finish_workout`: os exercícios do treino (na ordem) substituem os da rotina; séries = concluídas sem aquecimento; repetições = menor e maior das séries (iguais = fixas, diferentes = faixa); carga planejada = a maior; descanso e observação dos exercícios que já estavam na rotina são mantidos (novo: 90 s). Sem internet vai na mesma operação da fila (`{ kind: "finish", updateRoutine: true }`), que é idempotente.
- **Exercício adicionado no treino:** séries do último desempenho (`get_last_performance`), recorde de `get_exercise_records` e descanso de `routine_exercises.rest_seconds` (padrão 90s); sem internet, 3 séries vazias.
- **Observação de exercício:** salva no session_exercise e na `routine_exercises.notes`. Não passa para o próximo treino: lá ela aparece só como sugestão (placeholder) no campo da observação (`WorkoutExercise.previousNote`); a do treino novo começa vazia.
- **Unidade de peso:** `toDisplayWeight`/`fromDisplayWeight` em `packages/core/src/units.ts`; edição em lb com passo 5, em kg com passo 2; atalhos de repetições 6 / 8 / 10 / 12 / 15 (substituem; `QuickReps`); no teclado numérico o 1º dígito substitui o valor atual (`replaceOnFirstKey`); atalhos de carga rápida −1 / +1 / +5 / +10 (na unidade exibida).
- **Treino de hoje (projeto ativo):** pelos dias da semana das rotinas (`routines.weekdays`, ISO 1 = segunda … 7 = domingo no banco; na tela os dias aparecem de domingo a sábado — `WEEKDAYS` em schedule.ts). Rotina marcada para hoje → é o treino de hoje (várias no mesmo dia: a primeira pela ordem; as demais em "Trocar rotina"). O projeto usa dias e nenhuma rotina é de hoje → **dia de descanso** + o próximo treino da semana ("Amanhã" ou "Qua, 14 out"). Nenhuma rotina com dia marcado → a próxima pela ordem (`position`) depois da última concluída, voltando para a primeira; sem histórico, a primeira. Regra em `todayPlan` (`packages/core/src/schedule.ts`).
- **Card "Treino de hoje" (prioridade):** em andamento > concluído hoje > treino de hoje do projeto ativo **ou** dia de descanso > sem plano (tem rotinas, sem projeto ativo) > usuário novo (nenhuma rotina). No treino de hoje, abaixo de "N exercícios · N séries", uma linha discreta com relógio: "Média de 52 min nos últimos treinos" (`routineAverageLabel` em core/workout.ts, do `average_duration_seconds`; some se a rotina nunca foi treinada).
- **Gráfico de volume (comparação):** com variação = "+12% vs. período anterior"; sem treino no período anterior mas com histórico antes dele = "Sem treinos nas 4 semanas anteriores para comparar" (`CHART_PERIOD_LABELS[p].previous`); histórico que começou dentro do período atual ou período atual sem treino = a linha some (`missingComparisonKind` em core/history.ts). Antes aparecia "Sem dados do período anterior" para quem tinha acabado de começar.
- **Streak:** semana (dom–sáb) conta com ≥ 1 treino concluído; semana inteira sem treino zera. `weekly_goal` é só para exibição.
- **Textos do card de sequência** (constantes `STREAK_MESSAGES`, `streakWords` e `weeklyGoalLabel` em packages/core/src/home.ts, usadas na Início e no Histórico): número + "semanas" com "seguidas treinando" abaixo (lê-se "semanas seguidas treinando"); `week_secured` → "Semana garantida ✓" (o ✓ é o ícone Check do lucide) + "X de Y treinos da sua meta" quando houver meta; `streak_at_risk` → "Nenhum treino nesta semana ainda. Treine até sábado para manter sua sequência."; zerada ou usuário novo → "Treine 1 vez até sábado e comece sua sequência."; destaque dourado de recorde quando `current_streak` = `best_streak` e > 0.
- **Série concluída:** só conta o que foi marcado como concluído. Ao finalizar, `finish_workout` APAGA as séries não concluídas (e exercícios que ficaram sem séries) antes de calcular resumo e recordes; histórico, calendário, "anterior" e recordes leem só séries concluídas. O recorde só aparece ao concluir a série (`markRecordSets` ignora não concluídas e aquecimento) e fica numa série só por exercício: a de maior 1RM estimado do treino (bater de novo move o recorde para a nova série), como no `finish_workout`. Série com recorde: botão de concluir vira troféu dourado com brilho (`SheenOverlay`, o mesmo do botão principal).
- **Resumo de um treino:** volume = Σ carga × reps das séries concluídas sem aquecimento (mesma regra de `get_training_days`); "Séries" = séries concluídas sem aquecimento. Duração estimada da rotina = Σ séries × (40s + descanso), com padrão de 3 séries e 90s.
- **Tempo médio da rotina (calculado no banco):** campo calculado `average_duration_seconds` de `routines` (função SQL com parâmetro SEM nome, para o gen types incluí-lo no Row): média da duração efetiva (`active_seconds` ou fim − início) dos últimos treinos concluídos com a rotina, no máximo 5 (com 3, média dos 3); null se nunca treinada. Pedido no select das rotinas em `getHomeSummary` e `getProjectsOverview` (`averageDurationSeconds`). Exibição por `routineDurationLabel`/`routineMeta` (packages/core): "~52 min"; nunca treinada (null) → não mostra tempo. A tela de edição da rotina continua com a estimativa pelo plano (`estimateRoutineMinutes`).
- **1RM estimado:** Epley — carga × (1 + reps / 30), 1 casa (`estimate1RM` no core, idêntico ao `round(…, 1)` do banco). Aquecimentos não contam.
- **Recorde pessoal (PR) = maior 1RM estimado** (migration `20261020102933_personal_records_by_1rm`): subir a carga OU fazer mais repetições com a mesma carga conta. Um por exercício por treino, contra todos os treinos concluídos antes; empate não é recorde. Vale em todo lugar: tela do treino (`markRecordSets`, `best1RmKg` do `get_exercise_records.best_e1rm`), `finish_workout` (`personal_records` só `best_e1rm`, com `weight`/`reps` da série), resumo e folha do dia (`sessionRecord1Rm`), resumo offline, stories (a comparação "antes"/% usa o 1RM) e competição (`session_load_records`). O resumo mostra a série do recorde (carga × repetições).
- **Primeira vez de um exercício não gera PR.**
- **Senha do cadastro:** mínimo de 8 caracteres.

- Verde volt `#C6F432` = ação, seleção e conquista. Texto escuro sobre volt. No tema claro, textos/ícones usam verde mais escuro (contraste AA).

- Toques ≥ 44px; ações de treino ≥ 56px; ação principal na zona do polegar.
- **Interruptor (`Switch`):** a bolinha desliza (`translate`, parada com movimento reduzido) e o rótulo quebra linha. Em linha que já mostra o título (ex.: privacidade do perfil social), usar `hideLabel` (rótulo só para leitor de tela; antes o título aparecia duplicado). Linhas de Configurações com rótulo + controle usam `flex-wrap` (o controle desce em telas estreitas) e o texto de apoio só recua (`pl-12`) a partir de 360 px.
- Bottom navigation (5 abas): Início (com o histórico), Competir, Treinar (central), Projetos, Perfil. O destaque da aba ativa (tint volt 16%) é UM indicador que desliza e estica até a aba tocada (`useSlidingIndicator` em `shared/components/ds/navigation.tsx`, Web Animations API, sem biblioteca; mede o ícone da aba; movimento reduzido troca direto; some no item central). O `AppShell` move o indicador já no toque (`navIntent`), sem esperar a rota trocar.
- **Alertas no menu (bolinha):** `NavItem.badge` (`{ label }`; bolinha `bg-accent-text` no canto do ícone + texto só para leitor de tela). Quem gera o alerta é a feature, nunca o AppShell: publica com `usePublishNavAlert(aba, idDaFonte, { label } | null)` (`store/global/nav-alerts.store.ts`; abas em `NavAlertTab`, hoje só `"profile"`); o AppShell lê `useNavAlerts()` e junta os textos das fontes da mesma aba (`ALERT_TAB_LABELS`). As fontes ficam num componente que não desenha nada, montado em `app/(app)/layout.tsx` dentro do `AppShell` (ex.: `SocialNavAlerts`), porque as features que geram alertas importam o AppShell. Fonte atual: pedidos para seguir pendentes (`useFollowRequestsAlert`, `get_my_social().pending_requests_count`, conferido a cada 60 s com o app visível e ao voltar para ele; some ao responder os pedidos). Fonte nova = hook na feature + linha no componente de fontes; aba nova = valor em `NavAlertTab` e em `ALERT_TAB_LABELS`.
- **Avisos (`Banner`):** texto longo quebra linha e o botão desce para baixo dele quando não cabe ao lado (texto com `flex-[1_1_10rem]`, botão `flex-none`); botões curtos continuam ao lado. Nada sai do cartão.
- Acessibilidade WCAG AA, foco visível, labels acima dos campos.
- Sem emoji nem caractere unicode como ícone: usar ícones do lucide-react.
- **Logo:** sempre o componente `Logo` (SVG em traços, sem texto de fonte; geometria em `shared/components/ds/brand-geometry.ts`, igual a `assets/guf-logo-*.svg` do Claude Design). Cores pelos tokens: volt + texto no escuro, verde escuro AA + texto escuro no claro; `tone="mono"` herda a cor. Favicon: `src/app/icon.svg`.
- **Carregamento:** `GufLoader` (10 animações do símbolo "Anel"). Padrão do app: **08 (Cometa)** nos botões com `loading`; **09 (Sonar)** na abertura do app (`LoadingScreen`); **07 (Ponto saltitante)** no `SavingOverlay` ao salvar o treino. Telas que carregam conteúdo continuam com **skeleton** na silhueta da tela (como nos protótipos). Movimento reduzido: pulso de opacidade (classes `guf-motion-pulse`/`guf-motion-hide` em base.css).
- **Abertura do app:** `LoadingScreen` (logo animada + "Preparando seu treino") enquanto a sessão/aceites são verificados (`AuthSplash`) e, depois do login, até os dados da Início chegarem (uma vez por sessão, no `AppShell`). Sem internet não bloqueia (treino offline).
- **Símbolo da sequência:** `StreakFlame` (chama sólida, Claude Design "Streak Chama"; cor por `currentColor`, núcleo vazado por máscara). Ativo `text-accent-text`, zerada `text-fg-muted`, em risco `text-warning` com `animate="flicker"`. Animações de evento (`ignite`, `bump`, `milestone`, `out`) existem no componente e na vitrine (`/design-system#sequencia`), mas ainda não estão ligadas a eventos no app. Não usar `Zap` para sequência.
- **Músculos:** `MuscleIcon` (12 grupos, estático/animado/zoom) e `MuscleFilterTile` para filtros; código do banco → ícone com `muscleIconKey` (corpo inteiro e cardio sem ícone).
- **Seletor de exercícios** (`features/exercise-picker/`, usado no Treino e na Rotina): filtro por vários grupos com `MuscleFilterTile size="sm"` (cardio no fim, com o ícone `Activity`: o tile aceita `muscle` ou `icon` para grupos sem silhueta) (dica de rolagem uma vez por aparelho, `localStorage` "guf-muscle-filter-scrolled"), seções com `MuscleIcon`, exercícios em cartão com selo de equipamento e espaço reservado para a foto (selo + / ✓). Na Rotina, adicionar 1 exercício já abre o cartão dele.
- Ao implementar um design: a moldura de celular, a barra de status e o indicador de home do Claude Design são só apresentação e não entram no app.

## Convenções
- Código e nomes técnicos em inglês; textos da interface em português.
- **Nomes** (`.claude/patterns/nomenclatura.md`): arquivos e pastas em kebab-case; componentes em PascalCase; hooks com `use`; booleanos com `is`/`has`/`can`/`should`; constantes em SCREAMING_SNAKE_CASE; funções com verbo + substantivo (`get` = em memória, `fetch` = remoto, `build` = monta sem gravar, `format` = exibição, `to` = conversão). Sem abreviações, sem sufixo numérico (`v2`), sem `utils.ts` genérico. Stores em `*.store.ts`.
- **Funções:** um propósito por função (se o nome precisa de "e", são duas); guard clauses em vez de aninhamento profundo; números mágicos viram constantes nomeadas; `any` só com comentário justificando.
- **Comentários e documentação:** comentário explica o *porquê*, nunca o que a linha faz. Função exportada nova (principalmente em `packages/*`) ganha TSDoc de uma linha (`@param` sem repetir o tipo, `@returns`, `@throws` só o tratável).
- Commits: `feat:`, `fix:`, `chore:`, `refactor:`.
- Git: cada funcionalidade em sua própria branch (criada a partir da branch da etapa anterior); commit e push só quando pedido; nunca commitar `.env.local`.
- Antes de concluir uma tarefa: `pnpm lint`, `pnpm typecheck` e `pnpm build` sem erros, e a revisão de encerramento da `code-standards` (reler o diff, conferir quem consome o que mudou).
- Documentação junto com o código: mudou caminho, regra, fluxo ou contrato → atualizar no mesmo PR o documento da funcionalidade (`docs/features/`) ou a referência (`docs/reference/`), além de `docs/architecture.md` (estrutura), `business-rules.md` (regras) e `implementation-plan.md` (entregas e lacunas). Este `CLAUDE.md` recebe só regra que vale para o projeto inteiro e deve ficar abaixo de ~40 mil caracteres (o Claude Code avisa acima de 150 mil): funcionalidade nova = documento novo em `docs/features/` + uma linha no índice "Funcionalidades: onde ler os detalhes".
- Sempre encerrar o servidor de desenvolvimento que você iniciar ao terminar os testes.
- Mensagens de erro ao usuário: dizer o que aconteceu e como resolver.
- Ao mudar `compilerOptions` do apps/web, apagar `apps/web/tsconfig.tsbuildinfo` e `apps/web/.next/cache/.tsbuildinfo` (cache incremental guarda erros antigos).
